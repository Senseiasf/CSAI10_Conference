## 2. Критические ошибки и причины искажения эксперимента

### P0-1. Обучение и парный тест используют неправильную цену во всех 804 карточках

Место: `backend/app/scripts/generate_csai_tradeoffs.py`, `build_pair_record`, приблизительно строки 578–595; `backend/app/services/ltr_service.py`, `extract_candidate_features_v2`, строки 529–535.

Генератор передаёт в извлечение признаков отель и рейс, но не передаёт `breakdown` с рассчитанной стоимостью пакета. Поэтому вместо полной цены используется резервная формула:

```python
price = hotel_price_per_night * nights * rooms + 25000.0
```

При этом судье в карточке показывается полная цена, рассчитанная `assess`. В рабочем бенчмарке функция `features` передаёт настоящую стоимость через `breakdown`. Таким образом, обучение, парное тестирование и выдача работают с разным смыслом одного признака.

Результат проверки:

- 804 из 804 цен `features_v2.price` не совпадают с ценами карточек и расчётом каталога;
- 0 из 804 цен самих карточек расходятся с расчётом каталога;
- все маршруты карточек найдены; все карточки допустимы по реализованным жёстким правилам;
- пример пары № 1: A — 68 750 в признаках вместо 126 070 руб.; B — 118 100 вместо 227 180 руб.

Ошибка распространяется на логарифмы цены, цену за ночь, отношение категории отеля к стоимости и признаки доплаты. Исправление только отображаемой цены или только тестового JSON недостаточно. Нужен единый расчёт признаков из полной стоимости для генерации, обучения и применения, затем регенерация признаков всех разделов и переобучение. Метки нельзя автоматически заменять: сначала проверить, соответствовали ли исходные карточки намерению запроса.

### P0-2. Графики могут публиковать заданные в коде проценты при отсутствии результатов

Место: `backend/app/scripts/plot_csai_figures.py`, строки 49–63 и 109–129.

Если отсутствует нужный CSV, основной график использует `Success@1 = [3.5, 9.5, 61.0, 61.0, 61.0]`. Для holdout подставляются целиком готовые массивы метрик, включая `93.3` для C4. Более того, в этой подстановке C4 получает `Success@1 = 93.3`, а `Success@3 = 88.3`. Для одного критерия успеха и вложенной выдачи первое значение не может превышать второе.

Также отсутствующая конфигурация в таблице может молча превращаться в нулевой результат через `dict.get(..., 0.0)`; используются разные каталоги источников без обязательной проверки идентификатора прогона.

Необходимо прекращать построение графика с понятной ошибкой, если результаты отсутствуют, неполны или относятся к другому прогону. График должен быть исключительно представлением сохранённых измерений. Обязательные проверки: состав конфигураций, знаменатели, определение top-3, хеши входов, равенство источников таблиц и рисунков, `Success@1 <= Success@3`.

### P0-3. В режиме live предсказанные параметры заменяют эталон при оценке Success

Место: `backend/app/scripts/run_csai_benchmark.py`, строка 465:

```python
eval_ref = {**q, **(request or {})}
```

Если LLM ошиблась в бюджете, длительности или составе поездки, часть метрик оценивает пакет уже по ошибочным параметрам. Одновременно подробные ошибки пакетов и LFR/CSR вычисляются через `assess(route, q, ...)` по исходному сценарию. Поэтому возможны противоречивые результаты в одной записи.

Контрпример воспроизведён на маршруте `TOP3_01`: пакет неуспешен при эталонном бюджете 1 руб., но становится успешен после подстановки предсказанного бюджета 100 млн руб. Это контролируемая проверка механизма, а не утверждение о фактическом ответе LLM на этот запрос.

Эталон должен быть неизменяемым. Предсказанные параметры используются только как вход системы. Ошибки извлечения параметров следует измерять отдельно. В oracle-режиме влияние этого дефекта ограничено, однако утверждение о качестве полного агента требует исправления live-оценивания.

## 3. Предпочтения и эвристика

### P1-1. Качественное предпочтение исключается из Success, если не задан предел доплаты

Место: `run_csai_benchmark.py`, `offer_is_success`, строки 244–266. Проверка предпочтения выполняется только внутри условия `cap is not None`.

Пример `TOP3_05`: запрос содержит предпочтение завтрака без числового предела доплаты. Есть допустимый пакет с завтраком, но пакет без завтрака всё равно засчитывается как успешный. Аналогичные контрпримеры сохранены для `TOP3_09`, `TOP3_17` и других запросов.

Это расходится с ранее обсуждавшимся определением: предпочтение учитывается при наличии допустимого соответствующего варианта, а предел доплаты проверяется, **если задан**. Возможна другая научно допустимая постановка, где Success оценивает только жёсткие условия. Но тогда определение нужно явно изменить, а удовлетворение мягких предпочтений оценивать отдельно. Нельзя незаметно менять критерий после просмотра сравнительных результатов.

### P1-2. Разные части системы используют разный эталон доплаты

- `prioritize_preference` в `travel_preferences.py` сравнивает с минимальной ценой всего полученного пула.
- `offer_is_success` сравнивает с минимальной ценой внутри направления оцениваемого пакета.
- Генератор обучающих пар использует минимум **двух сравниваемых вариантов**.
- Рабочее извлечение признаков использует минимум **всего допустимого пула**.

Из-за этого пакет может удовлетворять одному правилу и не удовлетворять другому. После исправления цены останется сдвиг распределения: в обучающей паре один вариант обязательно минимален внутри пары, а при выдаче два сравниваемых варианта могут оба быть дороже общего минимума. Признаки одной карточки не должны произвольно меняться от выбора второго участника пары, если речь идёт об одном и том же запросе и пуле.

Нужно заранее определить экономический смысл доплаты: к какому варианту она относится, сравниваются ли разные направления и категории размещения, сумма указана на человека или на весь пакет. Затем применять одно правило к обучающим данным, постобработке и оценке. Эталон доступности предпочтения следует вычислять из зафиксированного каталога и сценария, независимо от того, какие альтернативы конкретная конфигурация нашла или потеряла.

### P1-3. Эвристика немонотонна по соответствию пожеланию

Место: `ltr_service.py`, `_surrogate_score`, строки 720–723:

```python
score += 0.85 * matches_time
score += 0.90 * matches_direct
if matches_time or matches_direct:
    score -= 1.5 * relative_surcharge
```

Штраф включается именно при появлении положительного признака. При одинаковой цене и остальных свойствах переход `matches_time: 0 -> 1` с `relative_surcharge = 1` уменьшает оценку на 0,65. Диагностический пример: **3,7252 -> 3,0752**. Это ошибка формулы, а не недостаток CatBoost.

Условия активации штрафа должны зависеть от запроса, а не от того, удовлетворил ли конкретный пакет пожелание. Желательны проверки монотонности на контролируемых изменениях цены, времени, числа пересадок и соответствия пожеланию. Численные веса нужно фиксировать заранее или выбирать по validation; нельзя ослаблять C3 ради выигрыша C4.

Также эвристика не использует флаг отсутствия расстояния до центра: неизвестное расстояние, представленное нулём, не получает штрафа и может оказаться выгоднее известного небольшого расстояния. Нужна согласованная обработка неизвестных значений, а не трактовка их как идеальных условий.

### P1-4. Часть пожеланий принципиально не представлена на входе CatBoost

В V2 есть признаки соответствия времени и прямому рейсу, но нет явного признака требуемого завтрака/повышения категории и нет размера разрешённой доплаты.

Воспроизведено: для одного пакета замена `max_extra_rub: 0` на `100000` не меняет вектор признаков. Замена пожелания `breakfast` на `stars` при остальных одинаковых параметрах также не меняет вектор. Модель не может выучить различие, которого нет в её входных данных. Поэтому дополнительное число деревьев не решает эту проблему.

Если эти пожелания полностью обслуживает общее детерминированное правило, это допустимо, но надо прямо описывать архитектуру «ранжировщик + политика предпочтений» и отдельно измерять вклад модели. Если ожидается обучение компромиссам самим CatBoost, нужны соответствующие признаки запроса и их взаимодействия со свойствами кандидата.

### P1-5. Постобработка заметно меняет результат, а не только оформляет выдачу

`prioritize_preference` при заданной доплате может перенести другой пакет на первое место. Без числового предела предпочитаемый вариант добавляется в начало списка альтернатив. `select_offers(diversify=True)` дополнительно резервирует место другим направлениям.

Это рабочая логика, а не само по себе нарушение. Но её эффект нельзя приписывать обученному ранжированию. Кроме того, `matches_preference(..., 'direct', ...)` проверяет только рейс туда. Нужно явно различать пожелание «прямой туда» и «прямой туда и обратно».

## 5. Выборки, разметка и статистика

### 5.1. Семейства разделены, но заявление о полном отсутствии пересечений неверно

| Раздел | Пар | Семейств | Типы компромиссов |
|---|---:|---:|---|
| Train | 192 | 10 | direct, time, stars |
| Validation | 105 | 5 | breakfast, time, direct, stars |
| Test | 105 | 5 | time, comfort, breakfast, direct |

Семейства действительно не пересекаются. Точных совпадений полных векторов признаков между разделами не найдено. Однако пересечения маршрутов по `route_key`: train–val — 3, train–test — 3, val–test — 6. Общий каталог сам по себе допустим для оценки обобщения на новые сценарии; это не автоматически недопустимая утечка. Но документ утверждает отсутствие пересечения маршрутов, что фактически неверно.

Train не содержит семейств `breakfast_vs_price` и `comfort_vs_price`, вместе составляющих 63/105 тестовых пар. `stars_vs_price`, напротив, отсутствует в тесте. Это смесь оценки новых семейств и переноса на не виденные в обучении типы компромиссов. Такой тест можно проводить, но его надо обозначать отдельно, а не называть полностью сбалансированным тестом одной распределённой одинаково задачи.

Все 402 пары содержат 25 уникальных текстов запросов. В test всего пять семейств по 21 паре. Нельзя интерпретировать 105 пар как 105 независимых пользовательских намерений. Например, преимущество C4 над ценой по семействам включает +100 п.п. на одном семействе и −100 п.п. на другом, практически взаимно компенсируясь.

Основные 200 и дополнительные 60 запросов имеют уникальные идентификаторы и тексты внутри каждого файла; точных текстовых дублей между файлами не найдено. Это не проверка семантической независимости или происхождения запросов.

### 5.2. Контрольные суммы и параметры разбиения не воспроизводят заявленный протокол

- Ни одна из трёх SHA256 для train/val/test не совпадает с `csai_tradeoffs_v2_split_meta.json`. Отдельно проверено: это не перевод строк CRLF; хеши Git-объектов также не совпадают с манифестом.
- `split_labeled_dataset` принимает `test_ratio` и `val_ratio`, но не использует их. При `test_ratio=0.1` и `0.4` получаются одни и те же размеры 192/105/105.
- Порядок выгрузки определяется обходом `set`, поэтому один `random seed` не фиксирует байтовое содержимое файлов между процессами с разным `PYTHONHASHSEED`.
- Встроенное разбиение `train_ltr.py` без отдельного `--eval-input` работает по ID пары, а не по семейству сценария. Это опасный запасной путь. Нельзя распространять гарантии отдельного family-split на любой запуск обучения.

Нужен детерминированный манифест с проверяемыми хешами и жёсткая проверка разделов перед обучением. Если доли задаются числом семейств на архетип, интерфейс должен честно отражать это правило.

### 5.3. Происхождение разметки недостаточно подтверждено

В файле присутствуют winner, confidence, rationale, key_tradeoff, judge_model и source; источник указан как `deepseek-flash`. Фактическое распределение — A: 213, B: 189, TIE: 0. Документ описывает другое распределение 261/141 и другие модели; это не подтверждённое описание текущего файла.

В сохранённом наборе нет достаточной истории запросов и сырых ответов, версии промпта, результатов перестановки A/B и полного манифеста запуска. Код разметчика умеет сохранять агрегат swap consistency, но в текущем файле такого агрегата нет. Не следует объявлять разметку выдуманной; следует считать её происхождение и устойчивость недостаточно аудируемыми.

Разметчик после ошибки API возвращает `winner='TIE'`, а при сохранении теряет отдельный статус ошибки. Это смешивает настоящую равноценность с неудачной разметкой. Такие состояния необходимо разделить и отчитываться о них независимо.

Нужна слепая независимая проверка части меток человеком, случайная стратифицированная перестановка A/B и учёт неоднозначности. Мягкие компромиссы без явно заданного ограничения цены не всегда имеют единственного объективного победителя.

### 5.4. Статистические заявления преждевременны

- `benchmark_csai_v2.py` проверяет C4 против C3, но не доказывает превосходства над ценой.
- Парный биномиальный тест считает пары независимыми, хотя они сгруппированы по пяти семействам. Нужны оценки неопределённости с группировкой на уровне сценариев/семейств и больше независимых семейств.
- Очень малый p-value округляется до `0.0`; лучше сохранять полное значение и выводить научную нотацию.
- При равных оценках и ценах парный тест всегда выбирает B. На идентичных карточках это воспроизведено. Основной бенчмарк учитывает полную ничью иначе — как половину успеха. Нужна единая симметричная политика ничьих.
- В основном бенчмарке `NDCG@2` считается на паре с одним положительным объектом. При такой разметке это практически преобразование парной точности, а не независимое измерение качества выдачи большого списка.
- Выборка пар, полученная только через `pareto_winner`, проверяет простое доминирование и не измеряет умение выбирать между ценой и качеством при реальном конфликте предпочтений.

Существующие документы уже обсуждают исправления под конкретные ID запросов holdout и результаты test. Эти наборы следует считать диагностическими/development, а не обещать, что они оставались закрытыми. Новый окончательный test нужно зафиксировать независимо после исправления протокола; нельзя перегенерировать его до выигрыша C4.

## 6. Что именно сравнивают C2-G, C3 и C4

Положительные изменения текущей ветки: у C2-G/C3/C4 один строгий пул и общая политика предпочтений; общий минимум для признаков берётся среди допустимых кандидатов; отсутствие модели C4 вызывает ошибку вместо незаметной замены эвристикой. Эти части не следует откатывать ради метрик.

Однако:

1. **C2 -> C2-G меняет несколько факторов:** источник маршрутов, строгую проверку, применение политики предпочтений и при соответствующем режиме разнообразие направлений. Рост качества нельзя приписать одному Neo4j. Для изоляции нужны одинаковые правила и политика при каталожной и графовой сборке либо более узкая формулировка вклада «графовая сборка + верификация».
2. В бенчмарке Neo4j извлекает пути, а основные проверки выполняет Python-функция `assess`. Проверка качества не доказывает, что аналогичный обход каталога/SQL невозможен. Польза графового представления требует отдельного обоснования структуры, расширяемости или вычислительных затрат.
3. Проверка совпадения графа и каталога сравнивает ключи маршрутов, а не все свойства: цена, вместимость и расписания могут отличаться при тех же ключах. Атрибуты отелей в `read_graph_routes` вообще подставляются из JSON. Нужна проверка полного снимка значимых свойств узлов и рёбер.
4. Фильтр и оценщик используют одни и те же правила `assess`. Поэтому 100% допустимости среди непустых строгих выдач во многом следует из конструкции. Нужен отдельный набор ожидаемых нарушений, рассчитанных независимо, включая граничные значения времени, вместимости и переправ.
5. Схема признаков C3 выбирается через глобальное состояние `LTRService`, установленное при загрузке модели C4. Смена V1/V2 может менять представление базовой эвристики. Для корректной абляции схема baseline должна быть явно зафиксирована независимо от исследуемой модели.
6. Стоимость обратного перелёта входит в тариф outbound `price_rub_roundtrip`, а сам обратный рейс выбирается отдельно по допустимости, авиакомпании и времени. Полноценные календарные даты, наличие мест, согласованность тарифа с выбранным обратным рейсом и временные зоны не моделируются. LFR характеризует выполнимость в принятой модели каталога, а не подтверждённую возможность реального бронирования.

Отдельно: `ranking_ms` в основном скрипте включает два вызова ранжирования — с политикой и без неё. Это стоимость диагностического измерения, а не задержка одного пользовательского ранжирования. Нужно отдельно замерять ранжировщик, политику и полный конвейер, с прогревом и распределением задержки.

## 7. Как получить честный следующий эксперимент

1. **Зафиксировать постановку до обучения.** Неизменяемый эталон; единицы бюджета и доплаты; правила мягких предпочтений; сравнимый базовый пакет; смысл direct; неизвестные значения; пустая выдача; один выбранный вариант Success@3. Отдельно определить случаи корректного отказа при отсутствии решения.
2. **Исправить вычисления и защиту результатов.** Единый конструктор пакета/цены/признаков; убрать искусственные 25 000 из экспериментального пути; исправить немонотонность C3; исключить подстановки процентов; отделить эталон от предсказанных параметров; закрепить симметричную обработку ничьих.
3. **Добавить независимые проверки свойств.** Полная цена из составляющих; одинаковые признаки одного пакета при генерации и применении; одинаковый пул C2-G/C3/C4; перестановочная инвариантность A/B; сохранение жёстких требований; границы 59/60 минут, capacity, дневного окна гидросамолёта и разводки мостов; некорректные/отсутствующие свойства; `Success@1 <= Success@3` для одной выдачи и одного критерия.
4. **Пересобрать данные по заранее заданной матрице.** Покрыть каждый тип компромисса и разные профили в train/validation; отдельно выделить перенос на новые типы/направления, если он является задачей исследования. Сохранять query/family ID и общий пул, из которого взята пара. Проверять точные и близкие дубликаты, происхождение карточек и согласованность меток. Долю неразрешимых запросов задавать заранее, не удалять их ради процента успеха.
5. **Разделить разработку и финальную проверку.** Текущие разобранные наборы оставить диагностическими. Новые семейства финального теста фиксирует независимая процедура/участник до просмотра результатов. Разделение должно предшествовать подбору весов C3 и параметров C4. Объединение двух старых файлов не делает тест новым или независимым.
6. **Переобучить все обучаемые сравнения на исправленных данных.** Сохранить версии признаков, модели, seed и гиперпараметры. Подбор только на validation; одинаковый доступ к настройке для эвристики и ML. Проверить несколько заранее выбранных seed. Нулевая важность отдельного признака сама по себе не является багом; нельзя обучать до получения желаемого рисунка важности.
7. **Разложить вклад компонентов.** Цена / эвристика / CatBoost на одном пуле; отдельно чистый порядок и общий слой предпочтений; отдельно разнообразие. Для вклада графа — одинаковая проверка и политика при сравниваемых способах сборки. Не смешивать Success@3 по score с Success@3 по diversified list в одной серии графиков.
8. **Выполнить интеграционный прогон реальных хранилищ.** Поднять чистые PostgreSQL/pgvector и Neo4j, выполнить seed, проверить свойства/эмбеддинги по хешам, прогнать официальный скрипт. Oracle-slots и live-LLM — разные эксперименты. Сохранить запросы, ответы, версии, таймауты и ошибки; секреты в артефакты не включать.
9. **Оценить неопределённость и опубликовать любой результат.** Парные различия по одинаковым запросам; интервалы и тесты с учётом семейств; числа успехов и знаменатели; ошибки по подгруппам; сравнение с ценой. Если C4 не выигрывает после исправлений, это результат исследования. Сам факт использования CatBoost не гарантирует превосходства над хорошей эвристикой.

По текущим данным нельзя достоверно решить, «переобучен ли CatBoost». Сначала надо устранить рассогласование признаков, недостающий контекст запроса и ошибки оценивания. Дальнейшая диагностика переобучения требует корректных train/validation learning curves и независимого теста. Простое изменение тестовой выборки или увеличение числа деревьев сейчас не устраняет найденные причины.

## 8. Артефакты и воспроизведение

Из корня проекта, с существующим окружением `.venv`:

```powershell
# Штатные тесты — из backend.
Push-Location backend
..\.venv\Scripts\python.exe -m pytest -q

# Сохранённые модели, исходный парный тест.
..\.venv\Scripts\python.exe -m app.scripts.benchmark_csai_v2 --output-dir ../experiment_outputs/review_f572e10/pairs
Pop-Location

# Целостность, контрпримеры, чувствительность цен, манифест.
$env:PYTHONIOENCODING = 'utf-8'
.\.venv\Scripts\python.exe audit/review_f572e10/check_invariants.py

# Диагностика по каталогу. Требуется уже скачанная модель MiniLM.
$env:HF_HUB_OFFLINE = '1'
$env:TRANSFORMERS_OFFLINE = '1'
.\.venv\Scripts\python.exe audit/review_f572e10/reproduce_audit.py
```

Основные файлы в `experiment_outputs/review_f572e10/`:

- `audit_manifest.json` — commit, версии библиотек и SHA256 входных файлов/моделей;
- `pairs/benchmark_summary.json` — исходный парный тест и предсказания по каждой паре;
- `price_correction_sensitivity.json` — фиксированные модели на пересчитанных ценовых признаках;
- `data_audit.json` — сверка 804 карточек с каталогом;
- `invariant_audit.json` — шесть нарушенных свойств, конкретные примеры и состав разделов;
- `additional_probes.json` — достижимость эталонных направлений, ничьи и отсутствие части контекста в признаках;
- `catalogue_query_results.json` — результаты каждого запроса и ранжировщика;
- `catalogue_summary.json` — агрегаты диагностического прогона.

Диагностические скрипты формируют отчёт о нарушениях; их нулевой код завершения означает завершение диагностики, **а не отсутствие обнаруженных дефектов**. Проверять нужно поля `invariants[].passed` и сам отчёт. Исходные экспериментальные файлы при этом не изменяются.
