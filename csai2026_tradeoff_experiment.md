# Проверка ранжирования туров при изменении предпочтения

## Что проверили

Цель — выяснить, способны ли текущие C3 и C4 выбрать разные варианты,
когда у пользователя меняется предпочтение, а кандидаты остаются прежними.
Проверка дополняет CSAI-200 и 182 диагностические пары доминирования.
Основной бенчмарк и текущие веса C4 в ходе эксперимента не изменялись.

Сформированы **416 пар** из связных маршрутов живого Neo4j. Обе стороны
каждой пары прошли те же жёсткие проверки, что и C3/C4. Дешёвый тур
уступает по одному из четырёх заданных преимуществ: прямой рейс туда,
категория отеля, завтрак или утренний вылет. Для перелёта сравнивались
туры в один и тот же отель через те же аэропорты с тем же типом и
названием трансфера. Для звёзд и завтрака совпадает рейс туда.

Для каждой пары созданы **два запроса**. Общее число гостей, длительность,
лимит на поездку и варианты A/B одинаковы. Меняется только максимальная
доплата за конкретное преимущество. Общий бюджет покрывает обе цены.
В одном запросе доплата допустима, в другом превышает указанный предел.
Поэтому эталонный выбор меняется. Другие различия в запросе объявлены
несущественными. Порядок A/B выбран до инференса. Никакие скоры C3/C4
не использованы для отбора или разметки.

Пример из теста — `turkey/pet/direct/1`. У тура A с пересадкой цена
327 800 ₽, у тура B с прямым рейсом — 345 000 ₽. Доплата 17 200 ₽.
При готовности доплатить до 8 000 ₽ правильный ответ A, при пределе
19 500 ₽ — B. В обоих запросах общий лимит 345 000 ₽.

## Разбиение и контроль

| Часть | Направления | Пары | Запросы |
| --- | --- | ---: | ---: |
| Train | Алтай, Мальдивы, Сочи, Таиланд | 145 | 290 |
| Validation | Египет, Грузия | 87 | 174 |
| Test | Санкт-Петербург, Турция, ОАЭ | 184 | 368 |

Тестовые пары по преимуществам — 40 для прямого рейса, 56 для звёзд,
28 для завтрака и 60 для утреннего вылета. Квота зависит от доступных
сопоставимых вариантов в каталоге. Два запроса каждой пары держатся в
одной части. Валидатор проверяет разделение по направлениям, уникальность
пар, цены, бюджет и согласованность эталона с порогом доплаты.

Замерены цена, действующая эвристика C3 и действующий CatBoost C4.
Дополнительно обучены два временных `CatBoostRanker` с одинаковыми
train/validation и стартовыми параметрами (PairLogit, лимит 300 деревьев,
глубина 5, learning rate 0,08, seed 42). Оба получают стандартные признаки
тура, тип преимущества, наличие преимущества и разницу цен. Второй
дополнительно получает предел доплаты пользователя. Количество деревьев
выбирается на validation. Веса временных моделей не подставляются в C4.

## Результаты на test

| Ранжировщик | Верных запросов | Точность | Пар, где верны оба ответа |
| --- | ---: | ---: | ---: |
| Цена | 184/368 | 50,0% | 0/184 |
| C3, текущая эвристика | 184/368 | 50,0% | 0/184 |
| C4, текущий CatBoost | 184/368 | 50,0% | 0/184 |
| Новый CatBoost без предела доплаты | 184/368 | 50,0% | 0/184 |
| Новый CatBoost с пределом доплаты | 354/368 | 96,2% | 170/184 |

Для пары со взаимно обратными ответами неизменный порядок туров
даёт ровно один правильный ответ из двух. Поэтому 50% в этом протоколе
означают, что ранжировщик **не реагирует на изменение предпочтения**.
Это не оценка средней точности на произвольном пользовательском трафике.
Контроль с новым CatBoost без предпочтения воспроизводит тот же потолок,
даже при наличии явного признака преимущества.

Контрольный CatBoost с предпочтением ошибся в 14 запросах: шесть для
категории отеля, четыре для завтрака, три для времени вылета и один для
прямого рейса. Отношение разрешённой доплаты к фактической в этих
случаях — от 0,68 до 1,18. Для явно заданного лимита доплаты обычное
сравнение цен выполняет точное правило. ML имеет смысл оценивать
отдельно на мягких предпочтениях, где у пользователя нет численного
правила выбора.

## Где теряется информация

В `LLMService` есть общий бюджет, требование прямого рейса и окно вылета.
Связки «предпочитаемый атрибут + условие, сколько за него готов
доплатить пользователь» в контракте нет. На вход ранжировщиков идут
архетип и признаки пакета. Например, фактический час вылета отсутствует
в признаках модели, а требование прямого рейса используется как жёсткое
ограничение. Один и тот же пользователь с тем же бюджетом и архетипом
может изменить решение, но оба ранжировщика получают прежние данные.

Доказанная причина в этом эксперименте — потеря контекста между запросом
и ранжированием. Дообучение на неизменном наборе признаков её не исправит.
Алгоритм CatBoost способен использовать недостающий признак, что видно
на контрольном прогоне. Это не исключает других ошибок весов C4, включая
нарушения доминирования, выявленные в предыдущем тесте.

Следующее изменение в агенте — отделить обязательные ограничения от
мягких условий, сохранить структурированное предпочтение и проверить,
что оно дошло до выбора. Явную доплату сравнивать с фактической
разницей цен. Для нечётких запросов нужен отдельный тест компромиссов
с независимой разметкой по исходным текстам и отдельными train/validation/test.

## Границы и воспроизведение

Это контролируемые синтетические запросы с однозначным эталоном.
Эксперимент проверяет слой выбора при известных условиях. Он не измеряет,
способен ли живой NLU извлечь предпочтение, и не заменяет тест с людьми.
Маршруты допустимы по правилам снимка каталога. У пар теста нет двух
трансферов с известной вместимостью, поэтому физическая вместимость
выбранных машин из этой проверки не следует.

Замороженный набор хранится в `backend/app/data/csai_tradeoff_dataset.json.gz`.
Для воспроизведения инференса и двух контрольных обучений из `backend/`:

```powershell
python -m app.scripts.run_csai_tradeoffs evaluate --dataset app/data/csai_tradeoff_dataset.json.gz
```

Для повторной сборки на заполненном Neo4j:

```powershell
python -m app.scripts.run_csai_tradeoffs prepare
python -m app.scripts.run_csai_tradeoffs evaluate
```

Выходы в `experiment_outputs/tradeoffs/`: итоговая таблица, предсказания
по каждому запросу, срезы по компромиссам, хеши и состав разбиений.
